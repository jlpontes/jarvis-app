# M1: o coração do Jarvis em Python, em 5 ideias

O M1 é o `core` (Command, Response, Module, Registry, Database), o módulo `tarefas`, a API com
login e o CLI. A arquitetura é a do C++. Abaixo, o que mudou de forma e por quê.

## 1. Uma declaração, quatro consumidores: `@action` ↔ `ActionInfo` + o `if` do `handle()`

No C++, cada ação aparece em três lugares: em `actions()` (nome e descrição), no `if` do
`handle()` e no parsing à mão do `args["texto"]`. Aqui ela é declarada **uma vez**:

```python
@action("add", "Adiciona uma tarefa", args=AddTaskArgs, result=Task, text_arg="title")
def add(self, ctx: Context, args: AddTaskArgs) -> Response[Task]: ...
```

Dessa linha saem:

- a rota `POST /api/tarefas/add`, com o corpo tipado no OpenAPI;
- os tipos do web (`make types`);
- o `jarvis help`, as opções `--due-date`/`--priority` do CLI e o `GET /api/modules`;
- no M5, a ferramenta da IA (o JSON Schema de `AddTaskArgs` vira o `input_schema`).

A cadeia de `if` some: a classe base `Module.handle()` acha a ação pelo nome, valida os
argumentos com o modelo e chama o método (`server/src/jarvis/core/module.py`).

## 2. A validação mora no modelo: `AddTaskArgs` ↔ `trim()` + `parse_id()` em `tasks_module.cpp`

No C++, `handle()` recebe texto livre e cada ação chama `trim()` e `parse_id()` à mão. Aqui, o
modelo Pydantic **é** a regra:

- `Title` tira os espaços e recusa vazio;
- `TaskId` aceita `3` e `"#3"` e recusa `"3abc"`, com a mesma mensagem do C++;
- `extra="forbid"` recusa campos desconhecidos.

Como CLI e HTTP passam pelo mesmo `registry.dispatch`, a regra é igual nos dois. Os erros do
Pydantic viram frases em português em `core/errors.py` ("Falta o campo Título.").

## 3. Uma conexão por requisição: `Context` ↔ o `Database&` guardado no módulo

O C++ abre o banco uma vez e guarda a referência no `TaskRepository` durante o `init()`. Isso
funciona porque o CLI faz uma coisa e termina. A API atende várias requisições ao mesmo tempo, em
threads diferentes, e uma conexão SQLite não deve ser usada por duas threads de uma vez. Então:

- `init(db)` só roda as migrations, uma vez na subida;
- cada requisição abre a própria conexão e a entrega à ação dentro de um `Context`, junto com o
  `now` (em UTC). "Hoje" é calculado no seu fuso (`ctx.today`);
- os testes passam um `now` fixo: "atrasada" e "hoje" ficam testáveis sem depender do relógio.

`BEGIN IMMEDIATE` + `busy_timeout` fazem as conexões esperarem a vez para escrever.
`test_concurrency.py` prova isso com 8 threads × 25 inserções.

## 4. `Response[T]` genérico ↔ `nlohmann::json data` + `to_json`

`Response[Task]` sabe o tipo de `data`. O resultado:

- o FastAPI descreve cada resposta no OpenAPI;
- o `schema.d.ts` do web ganha `Task` sozinho;
- não existe `to_json` escrito à mão.

`Response.success("…", task)` deduz o tipo pelo dado (`core/command.py`).

Os erros também são `Response`: a API nunca devolve o formato padrão do FastAPI
(`{"detail": …}`, status 422). Está tudo em `docs/contract.md`.

## 5. Login sem guardar sessão: cookie assinado (HMAC)

O cookie `jarvis_session` guarda só o instante do login mais uma assinatura HMAC-SHA256 feita
com `JARVIS_SECRET_KEY` (`api/auth.py`). Sem a chave, ninguém fabrica um cookie válido: o teste
`test_tampered_or_garbage_cookie_is_rejected` tenta. O servidor não guarda nada, e por isso:

- reiniciar a API não desloga ninguém;
- o logout apaga o cookie do navegador, mas uma cópia roubada vale até expirar. Para invalidar
  todas as sessões, troque a `JARVIS_SECRET_KEY`.

Outras proteções: senha e token comparados em tempo constante (`hmac.compare_digest`), 5
tentativas erradas por IP a cada 15 minutos, e a recusa de subir em produção com segredos de
exemplo ou curtos.

---

**A suíte de contrato** (`tests/contract/`) só fala HTTP. Ela sobe a API Python numa porta livre
ou aponta para outra URL (`make contract URL=...`). Quando o servidor C++ tiver
`POST /api/{modulo}/{acao}`, a mesma suíte vai dizer se ele cumpre o contrato.
