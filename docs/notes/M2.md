# M2: as tarefas no navegador, em 5 ideias

O M2 é o app web de verdade: login, a tela de Tarefas (agrupada, com edição, desfazer e
confirmação) e a casca de navegação. O servidor não mudou: o web só conhece o contrato HTTP.

## 1. O tipo vem do contrato: `call()` ↔ incluir o header da API

```ts
await call('/api/tarefas/editar', { id: 3, priority: 'high' })
```

`call` (`web/src/api/client.ts`) é genérico no **caminho**. A partir de `'/api/tarefas/editar'`,
o TypeScript procura em `schema.d.ts` (gerado do OpenAPI pelo `make types`) o corpo aceito
(`EditTaskArgs`) e o `data` da resposta (`Task`). Se você errar um campo, o erro aparece na
compilação, não no navegador. Nenhum tipo foi escrito à mão.

No C++ seria como um cliente que inclui o `.hpp` do servidor: se a assinatura muda, o cliente
para de compilar. A diferença é que aqui o "header" é gerado de uma fronteira de rede (o
OpenAPI). Por isso o servidor C++ pode substituir o Python sem tocar no web.

## 2. Estado do servidor ≠ estado da tela: TanStack Query

Existem dois tipos de estado:

- **da tela**: o sheet está aberto? "Concluídas" está expandida? Isso fica em `useState`.
- **do servidor**: a lista de tarefas. Ela não é do navegador, é uma *cópia* que pode estar velha.

O TanStack Query guarda essa cópia num cache com chave (`['tarefas', 'all']`). Ele busca de
novo quando você volta para a aba e mostra carregando, erro ou dados. Depois de uma mudança,
`invalidateQueries` diz "essa cópia ficou velha, busque de novo". Não existe `fetch` espalhado
pelos componentes, só `useTasks()` (`web/src/features/tasks/useTasks.ts`).

O C++ não tem equivalente, porque o CLI lê o banco direto a cada comando. O mais próximo seria
um `TaskRepository` com cache na frente que sabe quando invalidar.

## 3. Otimista com rollback ↔ `BEGIN` / `ROLLBACK`

Clicar em concluir não espera o servidor:

1. `onMutate`: guarda a lista atual (`previous`) e já marca a tarefa como feita no cache.
2. `mutationFn`: chama `POST /api/tarefas/feito`.
3. `onError`: devolve `previous` ao cache e mostra a `message` do servidor num aviso vermelho.
4. `onSettled`: invalida, e o servidor tem a última palavra.

É a mesma ideia da transação no `Database`: aplica, e se der errado volta ao estado guardado. O
`scope: { id: 'tarefas' }` põe as mutations numa fila, para que "concluir" e "desfazer" nunca
cheguem fora de ordem.

## 4. Sessão: o navegador não vê o segredo

O login grava um cookie `HttpOnly`: o JavaScript **não consegue lê-lo**, então um script
malicioso não rouba a sessão. Por isso o app pergunta à API se está logado (`GET /api/me`) em vez
de olhar o cookie. Qualquer 401 depois disso (por exemplo, sessão expirada) chama um handler que
limpa o cache e manda para `/login`, que depois volta para a página onde você estava. O 401 de
"senha incorreta" é tratado à parte, porque não significa "sessão expirou".

## 5. Uma identidade visual: tokens ↔ constantes num header só

Todas as cores estão em variáveis CSS (`--primary`, `--muted-foreground`…) em `web/src/index.css`,
com uma versão clara e uma escura escolhida por `prefers-color-scheme`. Os componentes nunca
usam uma cor solta, só `bg-primary`, `text-muted-foreground` etc. A escala de tipo (13/15/17/22/28 px)
também é definida ali, uma vez. Trocar o acento é mudar uma linha, como trocar uma `constexpr`
num header compartilhado. Os componentes do shadcn foram copiados para o repositório
(`components/ui/`), então são código nosso, que dá para ajustar.

## Testes do M2

- **Vitest**: as datas (`hoje`, `amanhã`, `sex 20/11`), o agrupamento e o client (mensagens de
  erro, 401, sessão).
- **Playwright** (`web/e2e/smoke.e2e.ts`): um navegador de verdade a 375 px faz login → adicionar
  → concluir → recarregar → continua lá, contra a API em modo produção com um banco temporário
  (`web/e2e/serve.sh`).
